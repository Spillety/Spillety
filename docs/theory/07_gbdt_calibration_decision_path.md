# 7. GBDT, калибровка и decision path

> **О чём этот блок простыми словами.**
> Мы уже умеем находить «похожие» кошельки и отсеивать ложные связи. Но остался главный вопрос: **как из всех этих сигналов получить одну понятную цифру риска — например, «вероятность 87%»?**
> Для этого нужна финальная модель. В Spillety это **GBDT** (ансамбль решающих деревьев) — потому что его можно объяснить в суде, откалибровать в честные вероятности и запустить на обычном CPU. Этот блок объясняет, как строится финальный скор и как из него получаются алерты разных уровней.

### Термины

| Термин | Определение |
|--------|-------------|
| GBDT | Gradient Boosting Decision Trees — ансамблевый метод машинного обучения, строящий последовательность решающих деревьев, каждое из которых исправляет ошибки предыдущих |
| LightGBM | Реализация GBDT с гистограммным обучением и leaf-wise ростом деревьев, оптимизированная для скорости и памяти |
| Decision path | Часть архитектуры, которая принимает финальное решение о риск-скоре; в Spillety — GBDT + калибровка |
| Калибровка | Преобразование выходов модели в вероятности, соответствующие реальной частоте событий |
| Reliability diagram | График, показывающий соответствие предсказанных вероятностей эмпирическим частотам |
| Brier score | Метрика калибровки: средний квадрат разности между предсказанной вероятностью и исходом |
| ECE | Expected Calibration Error — ожидаемая ошибка калибровки, взвешенная по размеру бинов |
| Isotonic regression | Непараметрический метод калибровки, строящий монотонную ступенчатую функцию |
| Beta calibration | Параметрический метод калибровки, устойчивый к малым выборкам и крайним значениям |
| SHAP | SHapley Additive exPlanations — метод интерпретации предсказаний модели через вклад каждого признака |
| Target | Целевая переменная, которую предсказывает модель; в Spillety — P(illicit in next window) |

## 7.1. Постановка задачи

> **Простыми словами.** У нас есть «сырьё» — десятки сигналов про кошелёк. Нужно «испечь пирог» — одну итоговую вероятность риска. И сделать это так, чтобы: (1) её можно было объяснить (для суда); (2) она была честной вероятностью, а не абстрактным баллом; (3) она считалась быстро, без GPU; (4) было видно, какие признаки повлияли на конкретный алерт.

В предыдущих блоках было показано, как получить embedding кошелька, объединить адреса в кластеры и отфильтровать spurious-связи через causal DAG. Retrieval возвращает top-K anchors, ближайших к кошельку, и для каждого anchor известны расстояние, тип, источник и sensitivity-метрики.

Однако остаётся открытым вопрос: **как из этих сигналов получить финальную оценку риска?**

Требования к финальной модели:

1. **Court-admissible:** модель должна быть интерпретируемой и объяснимой для регулятора и суда.
2. **Калибруемая:** выход модели должен быть вероятностью, а не произвольным скором.
3. **CPU-friendly:** inference должен работать на CPU.
4. **Интерпретируемая:** для каждого алерта должно быть понятно, какие признаки внесли вклад.

Этим требованиям удовлетворяет **GBDT** (Gradient Boosting Decision Trees). Deep learning не используется в decision path, потому что он не court-admissible: нельзя объяснить, почему нейросеть приняла то или иное решение.

> **Аналогия.** GBDT — это как комиссия из сотни простых экспертов, каждый из которых задаёт вопрос «да/нет» (например, «расстояние до OFAC меньше 0.15?»). Каждый следующий «эксперт» обучается исправлять ошибки предыдущих. Итог голосования — скор. Такое голосование легко объяснить: «риск высокий, потому что 30 из 100 экспертов сказали "да", и главный вклад дал признак X».

## 7.2. Почему GBDT, а не deep learning

> **Простыми словами.** Нейросеть — «чёрный ящик»: она хорошо предсказывает, но не может внятно объяснить, почему. Для банка и суда это неприемлемо. GBDT предсказывает не хуже, но зато каждый его шаг прозрачен.

| Критерий | GBDT | Deep learning |
|----------|------|---------------|
| Интерпретируемость | SHAP values, feature importance | Чёрный ящик |
| Court-admissibility | Установленный метод | Не установленный |
| Калибруемость | Isotonic, beta calibration | Требует дополнительных методов |
| CPU inference | Быстрый | Медленный без GPU |
| Малые выборки | Устойчив | Склонен к переобучению |
| Feature engineering | Прозрачный | Требует архитектуры |

**Ключевое:** GBDT — это **установленный метод** в финансовом моделировании. Его поведение предсказуемо и объяснимо. Deep learning в decision path создаёт регуляторное исключение (generative AI, SR 26-2).

**Где deep learning используется:** только для **retrieval** — обучения encoder'а (GraphSAGE), который выдаёт embeddings. Это не decision path, а представление данных.

> **Разделение ролей.** Нейросеть (GraphSAGE) — «переводчик»: превращает граф в векторы. GBDT — «судья»: выносит решение. Судья обязан быть понятным, переводчик — нет.

## 7.3. Feature engineering

> **Простыми словами.** Прежде чем «судить», нужно собрать «показания» — признаки. Их пять групп: расстояния до anchor'ов, типы anchor'ов, графовые свойства, временные паттерны и контекст (плюс sensitivity-признаки).

GBDT обучается на **табличных признаках**, извлечённых из retrieval.

### 7.3.1. Distances to top-K anchors

Основная группа признаков. Для каждого кошелька retrieval возвращает top-K ближайших anchors после causal filter.

| Признак | Как считается | Что отражает |
|---------|---------------|--------------|
| d_1...d_K | Расстояния до top-K anchors | Близость к известным точкам |
| mean, min, quantiles | Агрегаты расстояний | Общая близость |
| std | Стандартное отклонение | Разброс близости |

**Как получаем K:** PR-curve на retrieval task; K выбирается по cost-функции (см. §7.7).

### 7.3.2. Anchor types

| Признак | Как считается | Что отражает |
|---------|---------------|--------------|
| anchor_types_in_top_K | Типы anchors в top-K | К каким категориям близок |
| anchor_source_diversity | Число уникальных источников | Широта связей |
| distance_to_nearest_OFAC | Min distance to OFAC | Прямая близость к санкциям |
| distance_to_nearest_mixer | Min distance to mixer | Косвенная близость к миксерам |
| distance_to_nearest_exchange | Min distance to exchange | Близость к биржам |

### 7.3.3. Graph features

| Признак | Как считается | Что отражает |
|---------|---------------|--------------|
| PageRank | Итеративно на графе | Важность |
| in_degree, out_degree | Прямой подсчёт | Активность |
| velocity_24h | Транзакций за 24 часа | Интенсивность |
| counterparty_diversity | Уникальных контрагентов / всего | Розничный vs оптовый |

### 7.3.4. Temporal features

| Признак | Как считается | Что отражает |
|---------|---------------|--------------|
| Hawkes λ | MLE на истории | Само-возбуждение |
| time_since_last_tx | Прямой расчёт | Активность |
| burstiness | Coefficient of variation | Кластеризация |
| diurnal_pattern | FFT / hour-of-day | Геолокация (proxy) |

### 7.3.5. Contextual features

| Признак | Как считается | Что отражает |
|---------|---------------|--------------|
| news_co_mention_count | Подсчёт упоминаний | Публичность |
| exchange_proximity | Расстояние до exchange-кластеров | Инфраструктура |
| mixer_proximity | Расстояние до mixer-кластеров | Приватность |
| bridge_usage | Число bridge-транзакций | Cross-chain |

### 7.3.6. Sensitivity features

| Признак | Как считается | Что отражает |
|---------|---------------|--------------|
| causal_filter_pass_rate | Доля прошедших фильтр | Качество сигнала |
| e_value_max | Max E-value среди anchors | Устойчивость |
| rosenbaum_gamma_min | Min Γ* среди anchors | Устойчивость |
| sensemakr_r2_max | Max partial R² | Чувствительность |

**Итоговый feature vector:** ~50–100 признаков. Точное число определяется эмпирически через feature importance.

## 7.4. Модель: LightGBM

### 7.4.1. Почему LightGBM

> **Простыми словами.** LightGBM — конкретная, быстрая реализация GBDT. Она ест меньше памяти и обучается быстрее, чем XGBoost, и умеет работать с категориальными признаками «из коробки».

| Свойство | LightGBM | XGBoost |
|----------|----------|---------|
| Скорость обучения | Высокая (гистограммы) | Средняя |
| Память | Низкая | Средняя |
| Leaf-wise рост | Да | Нет (level-wise) |
| Категориальные признаки | Нативная поддержка | Требует кодирования |
| CPU inference | Быстрый | Быстрый |

**Leaf-wise рост:** LightGBM растёт деревья «в глубину», выбирая лист с наибольшим выигрышем. Это даёт лучшую точность при меньшем числе листьев, но требует контроля overfitting через `num_leaves` и `min_data_in_leaf`.

> **Аналогия.** Level-wise рост (XGBoost) — достраивать дерево «этаж за этажом». Leaf-wise (LightGBM) — «копать глубже там, где перспективнее». Второе эффективнее, но легче «перекопать», поэтому нужны ограничения.

### 7.4.2. Гиперпараметры

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| num_leaves | 31–127 | Контроль сложности |
| learning_rate | 0.01–0.1 | Скорость обучения |
| n_estimators | 100–1000 | Число деревьев |
| min_data_in_leaf | 20–100 | Контроль overfitting |
| feature_fraction | 0.7–0.9 | Случайный отбор признаков |
| bagging_fraction | 0.7–0.9 | Случайный отбор объектов |
| lambda_l1, lambda_l2 | 0–1 | Регуляризация |

**Как получаем гиперпараметры:** Optuna или Hyperopt на validation set; критерий — PR-AUC на hold-out temporal split.

### 7.4.3. Обучение

**Данные:** Elliptic++ + IBM AML + AMLSim. Temporal split для предотвращения утечки.

**Target:** P(illicit in next window). Определение illicit:

- OFAC-listed OR
- court-convicted OR
- under active investigation

> **Простыми словами про target.** Модель учится отвечать на вопрос: «какова вероятность, что этот кошелёк попадёт в "плохой" список в следующем временном окне?» Это и есть определение illicit.

**Классовый дисбаланс:** illicit-адресов мало (< 5%). Решение:

- `scale_pos_weight` в LightGBM.
- Focal loss (модификация для GBDT).
- Oversampling illicit (осторожно: может привести к overfitting).

**Как проверяем:** PR-AUC на hold-out; сравнение с baseline (XGBoost на Elliptic++).

## 7.5. Калибровка

### 7.5.1. Проблема

> **Простыми словами.** GBDT выдаёт «балл», а не вероятность. Балл 0.8 не значит «80% кошельков с таким баллом — плохие». Калибровка «выпрямляет» баллы так, чтобы 0.8 действительно означало 80%.

GBDT выдаёт **скор**, а не вероятность. Скор — это монотонная функция от log-odds, но не откалиброванная: скор 0.8 не означает, что 80% кошельков с таким скором являются illicit.

**Зачем калибровка:**

1. **Интерпретируемость:** аналитик должен понимать, что скор 0.8 — это 80% вероятность.
2. **Cost-функция:** threshold выбирается из PR-curve, которая требует калиброванных вероятностей.
3. **Регуляторное соответствие:** SR 26-2 требует калибровки.

### 7.5.2. Методы калибровки

**Isotonic regression:** непараметрический метод, строящий монотонную ступенчатую функцию \(f: \mathbb{R} \to [0, 1]\), минимизирующую squared error:

\[
\min_f \sum_{i=1}^{n} (y_i - f(\hat{p}_i))^2 \quad \text{при условии } f \text{ монотонна}
\]

где \(\hat{p}_i\) — скор модели, \(y_i\) — истинная метка.

**Преимущества:** гибкость, не предполагает форму. **Ограничения:** требует много данных; может переобучаться на малых выборках; плохо работает на крайних значениях.

**Beta calibration:** параметрический метод, моделирующий калибровочную функцию через бета-распределение:

\[
f(\hat{p}) = \frac{1}{1 + \exp\left(-a \log \frac{\hat{p}}{1 - \hat{p}} - b \log \hat{p} - c\right)}
\]

где \(a, b, c\) — параметры, оцениваемые на validation set.

**Преимущества:** устойчив к малым выборкам; хорошо работает на крайних значениях. **Ограничения:** предполагает конкретную форму.

### 7.5.3. Выбор метода калибровки

**Критерий:** ECE минимален, Brier устойчив.

**Процедура:**

1. Разбить данные на train/validation/test по времени.
2. Обучить GBDT на train.
3. Откалибровать isotonic и beta calibration на validation.
4. Оценить ECE и Brier на test.
5. Выбрать метод с минимальным ECE.

**Как проверяем:** reliability diagram на test; если кривая близка к диагонали, калибровка корректна.

## 7.6. Метрики калибровки

### 7.6.1. Brier score

\[
\text{Brier} = \frac{1}{n} \sum_{i=1}^{n} (\hat{p}_i - y_i)^2
\]

где \(\hat{p}_i\) — предсказанная вероятность, \(y_i\) — истинная метка (0 или 1).

**Интерпретация:** 0 — идеальная калибровка; 0.25 — случайный предиктор (при balanced classes). Для imbalanced классов Brier смещён; сравнение с тривиальным предиктором (предсказывающим base rate) обязательно.

### 7.6.2. ECE (Expected Calibration Error)

\[
\text{ECE} = \sum_{m=1}^{M} \frac{|B_m|}{n} \left| \text{acc}(B_m) - \text{conf}(B_m) \right|
\]

где \(B_m\) — бин \(m\) (например, 10 бинов по вероятности), \(\text{acc}(B_m)\) — эмпирическая точность в бине, \(\text{conf}(B_m)\) — средняя предсказанная вероятность в бине, \(n\) — общее число объектов.

**Интерпретация:** 0 — идеальная калибровка; > 0.1 — плохая калибровка. **Число бинов:** фиксировано (обычно 10–15).

### 7.6.3. Reliability diagram

> **Простыми словами.** График, где по оси X — предсказанная вероятность, по оси Y — реальная частота. Если точки лежат на диагонали — модель честна. Если выше диагонали — недооценивает риск, если ниже — переоценивает.

## 7.7. Выбор operating point

### 7.7.1. PR-curve

После калибровки строится **Precision-Recall curve**: для каждого порога \(\tau\) вычисляется precision и recall.

\[
\text{Precision}(\tau) = \frac{TP(\tau)}{TP(\tau) + FP(\tau)} \qquad
\text{Recall}(\tau) = \frac{TP(\tau)}{TP(\tau) + FN(\tau)}
\]

> **Простыми словами.** Precision — «из тех, кого поймали, сколько действительно виновны». Recall — «из всех виновных, сколько поймали». Повышая порог, мы ловим точнее, но меньше; понижая — ловим больше, но среди них больше невиновных.

### 7.7.2. Cost-функция

Порог \(\tau\) выбирается из PR-curve по **cost-функции**:

\[
\text{Cost}(\tau) = C_{FP} \cdot FP(\tau) + C_{FN} \cdot FN(\tau)
\]

где:

- \(C_{FP}\) — стоимость ложного срабатывания: время аналитика × стоимость часа. Оценивается из operational data.
- \(C_{FN}\) — стоимость пропуска: ожидаемый регуляторный штраф × вероятность. Оценивается из публичных enforcement actions и внутренней risk-модели.

**Operating point:** значение \(\tau\), минимизирующее \(\text{Cost}(\tau)\).

### 7.7.3. Budget constraint

При \(C_{FN}/C_{FP} \gg 1\) optimum стремится к \(\tau \to 0\): система будет алертить на всё. Решение — **budget constraint** на число алертов:

\[
\text{Alerts}(\tau) \leq B
\]

где \(B\) — максимальное число алертов, которое аналитики могут обработать. Threshold выбирается как максимум recall при constraint.

### 7.7.4. Пороги Tier 1/2/3

| Tier | Условие | Действие |
|------|---------|----------|
| Tier 1 | score > τ₁, causal passed, E-value > 2.0, Γ* > 1.5 | auto-block + SAR + human review |
| Tier 2 | τ₂ < score ≤ τ₁ | analyst review |
| Tier 3 | τ₃ < score ≤ τ₂ | async review, no blocking |
| Auto-clear | score ≤ τ₃ | no action, logged |

**Как получаем τ₁, τ₂, τ₃:** из PR-curve по cost-функции; τ₁ — порог для auto-block, τ₂ — для analyst review, τ₃ — для async review.

## 7.8. Интерпретируемость: SHAP values

### 7.8.1. Что такое SHAP

> **Простыми словами.** SHAP раскладывает итоговый скор на «вклад» каждого признака. Как разбор счёта в ресторане: видно, сколько именно добавил каждый пункт.

**SHAP** (SHapley Additive exPlanations) — метод интерпретации предсказаний модели через вклад каждого признака.

**Формально:** для предсказания \(f(x)\) и признака \(i\):

\[
\phi_i = \sum_{S \subseteq N \setminus \{i\}} \frac{|S|! (|N| - |S| - 1)!}{|N|!} (f(S \cup \{i\}) - f(S))
\]

где \(N\) — множество всех признаков, \(S\) — подмножество.

**Интерпретация:** \(\phi_i\) — вклад признака \(i\) в предсказание. Сумма всех \(\phi_i\) равна \(f(x) - \mathbb{E}[f]\).

### 7.8.2. Применение в Spillety

Для каждого алерта вычисляются SHAP values для top-10 признаков. Они включаются в evidence JSON:

```json
{
  "shap_values": {
    "distance_to_nearest_OFAC": -0.34,
    "causal_filter_pass_rate": 0.28,
    "e_value_max": 0.15,
    "anchor_source_diversity": 0.12
  }
}
```

**Зачем:** аналитик видит, какие признаки внесли вклад в алерт. Это необходимо для court-admissibility и для human review.

## 7.10. Ограничения

1. **Классовый дисбаланс:** illicit-адресов мало (< 5%). GBDT может смещаться в сторону majority class. Решение — `scale_pos_weight`, focal loss, oversampling.

2. **Temporal drift:** GBDT, обученный на исторических данных, деградирует при появлении новых паттернов. Требуется периодический retraining (см. блок 8).

3. **Калибровка на малых выборках:** isotonic regression требует много данных; beta calibration устойчивее, но предполагает форму.

4. **SHAP вычислительная сложность:** для больших ансамблей SHAP values вычисляются медленно. Решение — sampling-based SHAP (TreeSHAP для LightGBM).

5. **Отсутствие абсолютной интерпретации:** SHAP values показывают вклад признаков, но не причинность. Для причинной интерпретации требуется causal DAG (блок 6).

6. **Target definition:** P(illicit in next window) зависит от определения illicit. Если определение меняется (новые санкции, новые типы illicit), target требует пересмотра.

---

**Главная мысль:** GBDT — финальная модель decision path. Она обучается на табличных признаках из retrieval, калибруется через isotonic или beta calibration и интерпретируется через SHAP values.

| Компонент | Роль | Результат |
|-----------|------|-----------|
| LightGBM | Финальная модель | P(illicit in next window) |
| Feature engineering | Извлечение признаков из retrieval | ~50–100 признаков |
| Isotonic / beta calibration | Калибровка скоров | Калиброванные вероятности |
| Brier, ECE | Метрики калибровки | Оценка качества |
| PR-curve + cost | Выбор operating point | Пороги Tier 1/2/3 |
| SHAP values | Интерпретация | Вклад признаков |

**Практический вывод:**
- GBDT court-admissible, калибруем и интерпретируем; deep learning — нет.
- LightGBM — оптимальная реализация GBDT для CPU inference.
- Калибровка через isotonic или beta calibration; выбор по ECE/Brier.
- Operating point выбирается из PR-curve по cost-функции.
- SHAP values включаются в evidence JSON для каждого алерта.
- Target — P(illicit in next window); определение illicit: OFAC-listed OR court-convicted OR under active investigation.
