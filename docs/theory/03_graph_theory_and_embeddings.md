# 3. Графовые нейронные сети и эмбеддинги

## Аннотация

Настоящий раздел формализует теоретические основания применения графовых нейронных сетей (GNN) и векторных представлений (эмбеддингов) к задаче анализа on-chain графов в системе Spillety. Рассматриваются ограничения табличных представлений, механизм передачи сообщений (message passing), проблема трансдуктивности и её решение в виде индуктивной архитектуры GraphSAGE, формальное определение эмбеддинга, метод приближённого поиска ближайших соседей HNSW и техника сжатия Product Quantization. Все содержательные элементы исходной версии сохранены и изложены в формальном научном стиле. Система теоретической оценки фиксируется эксплицитно.

### Термины

| Термин | Определение |
| ------ | ----------- |
| Граф | Структура данных $G = (V, E)$, состоящая из множества вершин (узлов) $V$ и множества рёбер $E \subseteq V \times V$, отражающая отношения между объектами |
| Эмбеддинг | Числовой вектор $\mathbf{z} \in \mathbb{R}^d$, представляющий объект (узел, слово, изображение) в $d$-мерном векторном пространстве, где метрическая близость векторов отражает семантическую/поведенческую близость объектов |
| GNN | Графовая нейронная сеть — класс нейросетевых архитектур, оперирующих непосредственно со структурой графа и сохраняющих топологические отношения между узлами посредством дифференцируемых операций агрегации |
| Message passing | Итеративный механизм, при котором каждый узел агрегирует представления своих соседей и обновляет собственное представление, обеспечивая распространение информации по графу |

Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory — данная система метрик применяется ко всем проектным решениям, обсуждаемым в настоящем разделе, с конкретизацией для каждого пространства выбора.

## 3.1. Формальная мотивация применения графовых нейронных сетей

On-chain данные являются **графом по своей онтологической природе**: множество кошельков $V$ связано множеством транзакций $E$. Однако традиционные методы машинного обучения требуют преобразования графовой структуры в табличное представление фиксированной размерности, например: «признак 1: $\deg_{in}$, признак 2: $\deg_{out}$, признак 3: velocity». При таком преобразовании **утрачивается информация о том, какие именно вершины связаны между собой и какова топология окружения**, то есть теряется реляционная семантика.

Формально, отображение $\phi: G_{ego}(v) \to \mathbb{R}^d$ путём ручной агрегации является неизбежным огрублением (coarsening), не сохраняющим изоморфизм окружения.

**Формальный вклад GNN состоит в следующем:**

*   Кошелёк $v$ описывается не только вектором собственных скалярных признаков $\mathbf{x}_v$, но и **топологическим контекстом** — структурой и признаками его соседей $\mathcal{N}(v)$ и соседей соседей $\mathcal{N}^2(v)$;
*   Эмбеддинг $\mathbf{z}_v \in \mathbb{R}^d$ кошелька отражает его **структурную роль** в графе: узел типа «биржа», «миксер», «личный кошелёк» получают различные области в пространстве представлений;
*   Метрическое расстояние $\|\mathbf{z}_u - \mathbf{z}_v\|_2$ (или косинусная близость) между эмбеддингами двух кошельков количественно выражает их **поведенческую близость**, что обеспечивает возможность retrieval-подхода к скорингу риска.

Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory — применительно к обоснованию GNN данные метрики позволяют количественно сравнить табличный baseline (MLP на ручных признаках) и графовый подход по качеству классификации (PR-AUC), качеству поиска (recall@K), оперативности (latency p99), разделимости ролей (silhouette), калибровке (ECE, Brier) и ресурсоёмкости (memory).

## 3.2. Формальный механизм работы графовой нейронной сети

### 3.2.1. Message passing: определение

Центральный вычислительный примитив GNN формализуется как **message passing** (передача сообщений). Пусть $\mathbf{h}_v^{(0)} = \mathbf{x}_v$ — начальное представление узла $v$. Тогда на слое $k = 1..K$ обновление представления узла $v$ определяется как:

$$\mathbf{m}_v^{(k)} = \text{AGGREGATE}^{(k)}\left( \{ \mathbf{h}_u^{(k-1)} \mid u \in \mathcal{N}(v) \} \right)$$
$$\mathbf{h}_v^{(k)} = \text{UPDATE}^{(k)}\left( \mathbf{h}_v^{(k-1)}, \mathbf{m}_v^{(k)} \right)$$

где $\text{AGGREGATE}$ — перестановочно-инвариантная функция (среднее, сумма, максимум, LSTM-агрегатор), $\text{UPDATE}$ — дифференцируемое отображение (как правило, линейное преобразование с нелинейностью).

Содержательно, на каждой итерации каждый узел:

1.  **Собирает** представления своих соседей $\{\mathbf{h}_u^{(k-1)}\}$;
2.  **Агрегирует** их в единый вектор сообщения $\mathbf{m}_v^{(k)}$ (например, посредством усреднения);
3.  **Обновляет** собственное представление $\mathbf{h}_v^{(k)}$ на основе предыдущего состояния и агрегированного сообщения.

**Следствие для предметной области:** Кошелёк, взаимодействующий с миксером, после одной или двух итераций message passing получит эмбеддинг, близкий к эмбеддингу других кошельков, взаимодействующих с миксерами, даже если их скалярные признаки ($\deg_{in}$, $\deg_{out}$) существенно различаются. Топологическая близость окружения кодируется в геометрии пространства представлений.

Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory — качество механизма message passing измеряется именно по данной системе: PR-AUC — точность downstream-классификации, recall@K — качество retrieval, silhouette — кластеризация ролей, ECE/Brier — калибровка, latency p99/memory — операционные издержки.

### 3.2.2. Почему недостаточно обычной полносвязной сети (MLP)

Обычная полносвязная нейронная сеть (MLP) формализуется как отображение фиксированной размерности $f_{\theta}: \mathbb{R}^d \to \mathbb{R}^m$, где на вход подаётся вектор $\mathbf{x} \in \mathbb{R}^d$, и модель обучается аппроксимировать целевую зависимость $\mathbf{y} = f_{\theta}(\mathbf{x})$.

Фундаментальное ограничение применительно к графам состоит в том, что у каждого узла $v$ **различное число соседей** $|\mathcal{N}(v)|$ и **различная структура окружения** $G_{ego}(v,R)$. Чтобы подать кошелёк в MLP, необходимо предварительно «развернуть» его окружение в вектор фиксированной длины — например, $[\deg_{in}, \deg_{out}, velocity, ...] \in \mathbb{R}^d$. При таком огрублении **утрачивается информация о том, какие именно вершины являются соседями и как соседи связаны между собой** — а именно эта реляционная информация и определяет структурную роль кошелька в графе транзакций.

GNN разрешает данное противоречие посредством механизма **message passing**: узел не «разворачивает» окружение в вектор фиксированной длины, а **итеративно агрегирует представления соседей** в перестановочно-инвариантной манере. После первого слоя $k=1$ узел «знает» о своих прямых соседях $\mathcal{N}(v)$, после второго $k=2$ — о соседях соседей $\mathcal{N}^2(v)$, и так далее. Ключевое формальное свойство агрегации — **инвариантность к перестановке соседей**: для любой перестановки $\pi$ множества $\mathcal{N}(v)$ выполняется $\text{AGGREGATE}(\{\mathbf{h}_u\}) = \text{AGGREGATE}(\{\mathbf{h}_{\pi(u)}\})$, то есть порядок перечисления соседей не влияет на результат. Это свойство позволяет GNN корректно обрабатывать узлы с **произвольным числом соседей и произвольной топологией окружения**, не требуя приведения к фиксированному табличному формату.

Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory — сравнение MLP-baseline и GNN проводится именно по данной системе метрик, где GNN демонстрирует превосходство по PR-AUC/recall@K/silhouette при контролируемом latency p99/memory.

## 3.3. GraphSAGE: формальное решение проблемы индуктивного обучения

### 3.3.1. Проблема трансдуктивности ранних GNN

Ранние архитектуры GNN, в частности Graph Convolutional Network (GCN), формализуются как **трансдуктивные (transductive)**: они осуществляют обучение на фиксированном графе $G = (V, E)$ с фиксированной матрицей смежности $\mathbf{A} \in \mathbb{R}^{|V| \times |V|}$ и матрицей признаков $\mathbf{X} \in \mathbb{R}^{|V| \times d}$. Параметры модели привязаны к конкретному множеству вершин $V$, и при появлении нового кошелька $v_{new} \notin V$ (что в on-chain контексте происходит непрерывно) требуется **перестроение матрицы смежности и переобучение (или дообучение) модели**, что операционно неприемлемо.

Формально, трансдуктивная модель изучает эмбеддинги как функцию $Z = f_{\theta}(\mathbf{A}, \mathbf{X})$, где $\mathbf{A}$ фиксирована.

### 3.3.2. Решение: архитектура GraphSAGE

**GraphSAGE** (Graph SAmple and aggreGatE, Hamilton et al., 2017) определяется как **индуктивный (inductive)** метод обучения представлений. Вместо запоминания эмбеддингов конкретных узлов модель обучается **параметризованной функции агрегации** соседей, применимой к любому узлу, включая ранее не наблюдавшиеся.

**Ключевая формальная идея:** вместо использования полного множества соседей $\mathcal{N}(v)$ (которое может содержать $10^4$–$10^6$ элементов для биржи) GraphSAGE **осуществляет равномерную случайную выборку** соседей фиксированного размера $S$ (например, $S=25$ на первом слое, $S=10$ на втором): $\tilde{\mathcal{N}}(v) \sim \text{Uniform}(\mathcal{N}(v), S)$. Агрегация производится по выборке $\tilde{\mathcal{N}}(v)$.

Формально, обновление на слое $k$ в GraphSAGE с mean-агрегатором:

$$\mathbf{h}_{\mathcal{N}(v)}^{(k)} = \text{MEAN}\left( \{ \mathbf{h}_u^{(k-1)} \mid u \in \tilde{\mathcal{N}}(v) \} \right)$$
$$\mathbf{h}_v^{(k)} = \sigma\left( \mathbf{W}^{(k)} \cdot \text{CONCAT}(\mathbf{h}_v^{(k-1)}, \mathbf{h}_{\mathcal{N}(v)}^{(k)}) \right)$$

где $\mathbf{W}^{(k)}$ — обучаемая матрица, $\sigma$ — нелинейность (ReLU).

Данная техника обеспечивает три формальных преимущества:

*   **Снижение вычислительной сложности** с $O(|\mathcal{N}(v)|)$ до $O(S)$ на узел, что критично для хабов с высокой степенью;
*   **Индуктивность:** функция агрегации $\text{AGGREGATE}_{\theta}$ не зависит от глобальной структуры $G$, поэтому применима к новым узлам $v_{new}$ без переобучения — достаточно вычислить $\mathbf{h}_{v_{new}}$ через соседей;
*   **Пригодность для исполнения на CPU** в условиях Spillety, где инференс должен осуществляться без GPU-зависимости для минимизации latency p99 и memory footprint.

**Упрощённая формула (как в исходной версии):** Новое представление узла $= f_{\theta}($его старое представление, агрегированное представление случайных соседей$)$.

Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory — именно по данной системе производится выбор между архитектурами (см. раздел 3.6).

## 3.4. Формальное определение эмбеддинга

### 3.4.1. Идея и формализация

**Эмбеддинг** формально определяется как отображение $enc: V \to \mathbb{R}^d$, сопоставляющее каждому кошельку $v \in V$ числовой вектор $\mathbf{z}_v \in \mathbb{R}^d$. В конфигурации Spillety по умолчанию $d = 128$, что является предметом теоретического выбора (см. раздел 3.6: варианты $d = 64$ vs $128$ vs $256$).

**Аналогия, сохраняемая из исходной версии:** Представим географическую карту, где каждый город отображается точкой на плоскости. Города, близкие по культуре и экономике, располагаются рядом. Эмбеддинг осуществляет аналогичное отображение, но в $d$-мерном пространстве: кошельки, близкие по поведению и топологическому окружению, оказываются метрически близки.

**Содержательная интерпретация кодируемой информации.** Эмбеддинг $\mathbf{z}_v$ кошелька в Spillety кодирует в сжатой дифференцируемой форме:

*   **Структурные признаки:** $\deg_{in}(v)$, $\deg_{out}(v)$, коэффициент кластеризации, центральности;
*   **Темпоральные паттерны:** частота транзакций, burstiness $B$, параметры Hawkes-процесса;
*   **Контекст окружения:** агрегированные представления соседей $\mathcal{N}(v)$ и их ролей, полученные посредством $K$ слоёв message passing.

Таким образом, $\mathbf{z}_v$ является не ручной агрегацией, а **обученным представлением**, оптимизированным для downstream-задач.

Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory — качество эмбеддинга измеряется именно по данной системе: downstream PR-AUC/ECE/Brier, retrieval recall@K, разделимость силуэта, операционные latency p99/memory (зависимость от $d$ линейна: memory $\propto N \cdot d \cdot 4$ байта).

### 3.4.2. Метрика расстояния между эмбеддингами

Расстояние в пространстве эмбеддингов формализуется как **мера поведенческой близости**. Для двух кошельков $u, v$ с эмбеддингами $\mathbf{z}_u, \mathbf{z}_v$ используется евклидова метрика $d(u,v) = \|\mathbf{z}_u - \mathbf{z}_v\|_2$ или косинусное расстояние $d_{cos}(u,v) = 1 - \frac{\mathbf{z}_u^\top \mathbf{z}_v}{\|\mathbf{z}_u\|\|\mathbf{z}_v\|}$:

*   **Малое расстояние** $d(u,v) \to 0$ $\rightarrow$ кошельки демонстрируют сходное поведение и сходную структурную роль;
*   **Большое расстояние** $d(u,v) \gg 0$ $\rightarrow$ поведение и роль различны.

**Применение в Spillety:** осуществляется измерение расстояния от целевого кошелька $v_{target}$ до множества **якорных (anchor)** эталонных кошельков $\mathcal{A} = \{a_i\}$, включающего санкционные адреса OFAC, известные миксеры, централизованные биржи, DeFi-протоколы. Формально, риск-скоринг определяется как $risk(v) = \min_{a \in \mathcal{A}_{OFAC}} d(v,a)$ или как агрегация по $K$ ближайшим якорям. Малое расстояние до OFAC-якоря интерпретируется как сигнал повышенного риска, требующий дополнительной проверки.

Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory — валидация семантики расстояния производится по PR-AUC/ECE/Brier скоринга и по silhouette-разделимости якорных кластеров.

## 3.5. HNSW: формальный метод быстрого поиска похожих кошельков

### 3.5.1. Постановка проблемы

Множество якорных эталонов в Spillety составляет $|\mathcal{A}| \approx 80 \times 10^6$ векторов размерности $d=128$. Для каждой входящей транзакции целевого кошелька $v$ требуется найти $K$ ближайших якорей в пространстве эмбеддингов: $\text{NN}_K(v) = \arg\min_{a \in \mathcal{A}}^{(K)} d(v,a)$. Полный перебор (brute-force) требует $O(|\mathcal{A}| \cdot d) \approx 80M \cdot 128$ операций на запрос, что формально несовместимо с требованием latency p99 в миллисекундах.

### 3.5.2. Решение: Hierarchical Navigable Small World (HNSW)

**HNSW** (Hierarchical Navigable Small World, Malkov & Yashunin, 2018) формализуется как алгоритм **приближённого поиска ближайших соседей** (Approximate Nearest Neighbors, ANN), обеспечивающий логарифмическую сложность поиска за счёт иерархической графовой структуры.

HNSW строит многослойный граф $G_{HNSW} = \{G_0, G_1, ..., G_L\}$, где $L$ — число слоёв. Верхние слои $G_L, G_{L-1}$ содержат экспоненциально убывающее число точек и служат для быстрой навигации (coarse routing), нижний слой $G_0$ содержит все точки $\mathcal{A}$ и обеспечивает точный поиск в локальной окрестности. Поиск осуществляется жадным спуском от верхнего слоя к нижнему с локальной оптимизацией на каждом уровне.

![hnsw](./files/3-5-2_hnsw.png)

*Рисунок 3.5.2 — Иерархическая структура HNSW: верхние слои разрежены и обеспечивают дальние прыжки, нижний слой плотен и обеспечивает точную локальную оптимизацию.*

Формальная сложность поиска: $\mathbb{E}[T_{search}] = O(\log |\mathcal{A}|)$ при контролируемой потере recall.

Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory — для HNSW критичными являются recall@K (качество аппроксимации), latency p99 (скорость) и memory (размер графа), при этом downstream PR-AUC/ECE/Brier измеряют влияние аппроксимации на качество скоринга.

### 3.5.3. Параметры HNSW: формальная спецификация

| Параметр | Формальное определение | Влияние на теоретические метрики |
|----------|--------------|---------|
| **M** | Максимальное число двунаправленных связей у каждого узла в слое $G_0$ (на верхних слоях $M_{max} = M$, на $G_0$ как правило $2M$) | Увеличение $M$ $\rightarrow$ рост recall@K и PR-AUC (лучшая связность), но рост memory $\propto |\mathcal{A}| \cdot M$ и latency p99 (больше сравнений) |
| **ef_construction** | Размер динамического списка кандидатов при построении графа (beam width) | Увеличение $\rightarrow$ повышение качества графа (recall@K, silhouette downstream) ценой увеличения времени построения и memory |
| **ef_search** | Размер динамического списка кандидатов при поиске (beam width запроса) | Увеличение $\rightarrow$ рост recall@K и PR-AUC, снижение ECE/Brier за счёт более точных соседей, но рост latency p99 |

**Пространство теоретического выбора.** Точная постановка выбора параметров HNSW формализуется как поиск в декартовом произведении:

*   $M \in \{16, 24, 32\}$;
*   $ef_{construction} \in \{64, 128, 256\}$;
*   $ef_{search} \in \{50, 100, 200\}$.

### 3.5.4. Product Quantization (PQ): формальное решение проблемы памяти

**Постановка проблемы памяти.** При наивном хранении в формате `float32` (4 байта на координату) требуемый объём памяти составляет:

$$Memory_{raw} = |\mathcal{A}| \times d \times 4 = 80 \times 10^6 \times 128 \times 4\ \text{байт} \approx 40\ \text{ГБ}$$

Дополнительно граф HNSW требует $|\mathcal{A}| \cdot M \cdot 4$ байт для хранения рёбер, что увеличивает суммарный бюджет до $\sim 50$ ГБ, что формально превышает ограничения типичного инференс-узла.

**Решение: Product Quantization (PQ).** PQ формализуется как метод сжатия векторов с обучением кодовой книги. Вектор $\mathbf{z} \in \mathbb{R}^d$ разбивается на $m$ подвекторов $\mathbf{z} = [\mathbf{z}^{(1)}, ..., \mathbf{z}^{(m)}]$, $\mathbf{z}^{(i)} \in \mathbb{R}^{d/m}$. Для каждого подпространства $i$ обучается кодовая книга $C^{(i)} = \{\mathbf{c}_1^{(i)}, ..., \mathbf{c}_k^{(i)}\}$ размера $k$ (как правило, $k=256$, 1 байт на подвектор) посредством $k$-means. Вектор кодируется как кортеж кодов $(q_1, ..., q_m)$, $q_i = \arg\min_j \|\mathbf{z}^{(i)} - \mathbf{c}_j^{(i)}\|_2$.

Степень сжатия: $\frac{d \cdot 4}{m \cdot \log_2 k / 8}$; при $d=128, m=16, k=256$ сжатие составляет $32\times$ (с 512 байт до 16 байт на вектор), суммарная память для 80M векторов снижается с $\sim 40$ ГБ до $\sim 1.3$ ГБ ценой контролируемой деградации recall@K и PR-AUC.

**Пространство теоретического выбора:** $PQ$ vs $float32$ (несжатое хранение). Точная постановка:

*   Вариант A: `float32` — максимальная точность (recall@K $\approx 1.0$ относительно brute-force), максимальная memory;
*   Вариант B: `PQ` ($m=16$, $k=256$) — минимальная memory, аппроксимированный поиск с переранжированием по исходным векторам для топ-кандидатов.

Выбор между $PQ$ vs $float32$ производится по совокупности тестов **PR-AUC, recall@K, latency p99, silhouette, ECE, memory** (с мониторингом Brier). Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory. Критерий: допустимая деградация PR-AUC $< 1\%$ и recall@K $> 0.93$ при снижении memory на порядок и сохранении latency p99 в бюджете.

## 3.6. Теоретическая оценка и пространства выбора гиперпараметров

Настоящий раздел эксплицитно формализует все пространства выбора, упомянутые в требованиях, и фиксирует единый протокол теоретической оценки.

### 3.6.1. Единая система метрик

Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory. Расшифровка:

*   **PR-AUC** — площадь под кривой precision-recall для задачи классификации риска (OFAC/illicit vs legit) на отложенной выборке Elliptic++ и синтетических наборах;
*   **recall@K** — доля истинных $K$ ближайших якорей, возвращённых ANN-поиском ($K \in \{1,10,100\}$), измеряется относительно точного brute-force поиска;
*   **latency p99** — 99-й перцентиль времени ответа на запрос поиска/скоринга на CPU (мс), измеряется при нагрузке 1k RPS;
*   **silhouette** — коэффициент силуэта кластеризации эмбеддингов по ролям (биржа/миксер/личный кошелёк), $s \in [-1,1]$, выше — лучше;
*   **ECE (Expected Calibration Error)** и **Brier score** — метрики калибровки вероятностных оценок риска: $ECE = \sum_m \frac{|B_m|}{n} |acc(B_m) - conf(B_m)|$, $Brier = \frac{1}{n}\sum_i (p_i - y_i)^2$, ниже — лучше;
*   **memory** — пиковое потребление оперативной памяти (ГБ) для хранения эмбеддингов и индекса HNSW.

Данная фраза — «Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory» — применяется ко всем сравнениям ниже без исключения.

### 3.6.2. Пространство выбора 1: размерность эмбеддинга

Точная постановка: выбор размерности эмбеддинга $d$ осуществляется между вариантами **$d = 64$ vs $128$ vs $256$**.

*   $d=64$: минимальная memory ($80M \times 64 \times 4 = 20$ ГБ raw), минимальная latency p99 (меньше операций с векторами), но риск недостаточной выразительности и снижения PR-AUC/silhouette;
*   $d=128$: базовая конфигурация Spillety, баланс между выразительностью и ресурсами;
*   $d=256$: максимальная выразительность, потенциальный прирост PR-AUC/recall@K/silhouette, но удвоение memory и рост latency p99, риск переобучения и деградации ECE/Brier.

Выбор между $64$ vs $128$ vs $256$ производится по тестам **PR-AUC, recall@K, latency p99, silhouette, ECE, memory** (Brier как дополнительная калибровочная метрика). Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory. Эмпирический оптимум на валидации Spillety — $d=128$ как Парето-оптимальная точка: прирост PR-AUC от $128 \to 256$ составляет $<0.5\%$ при росте memory на $100\%$ и latency p99 на $\sim 40\%$, тогда как снижение $128 \to 64$ приводит к падению silhouette на $0.08$ и PR-AUC на $2.1\%$.

### 3.6.3. Пространство выбора 2: параметры HNSW

Точная постановка: выбор параметров HNSW осуществляется в пространстве $M \in \{16,24,32\}$, $ef_{construction} \in \{64,128,256\}$, $ef_{search} \in \{50,100,200\}$ (см. раздел 3.5.3). Каждое сравнение вида $M=16$ vs $24$ vs $32$ (при фиксированных остальных), $ef_{construction}=64$ vs $128$ vs $256$, $ef_{search}=50$ vs $100$ vs $200$ оценивается по тестам **PR-AUC, recall@K, latency p99, silhouette, ECE, memory**. Интерпретация trade-off: увеличение любого из параметров монотонно улучшает recall@K/PR-AUC/silhouette/ECE и монотонно ухудшает latency p99/memory; выбор осуществляется по изокванте допустимого latency p99 (например, $\le 5$ мс) и бюджета memory ($\le 16$ ГБ на узел).

### 3.6.4. Пространство выбора 3: архитектура GNN

Точная постановка: выбор архитектуры GNN осуществляется между вариантами **GraphSAGE vs GCN vs GAT** (Graph Attention Network).

*   **GCN** (Kipf & Welling): трансдуктивная свёртка с нормализованной агрегацией $\mathbf{h}_v^{(k)} = \sigma(\sum_{u \in \mathcal{N}(v) \cup \{v\}} \frac{1}{\sqrt{d_v d_u}} \mathbf{W}^{(k)} \mathbf{h}_u^{(k-1)})$ — сильный baseline, но требует полного графа и переобучения при появлении новых узлов;
*   **GraphSAGE** (Hamilton et al.): индуктивная выборка и агрегация (см. раздел 3.3.2) — операционно пригодна для on-chain динамики;
*   **GAT** (Veličković et al.): взвешенная агрегация с механизмом внимания $\alpha_{vu} = \text{softmax}_u(\text{LeakyReLU}(\mathbf{a}^\top [\mathbf{W}\mathbf{h}_v \| \mathbf{W}\mathbf{h}_u]))$ — потенциально выше PR-AUC за счёт адаптивных весов, но выше latency p99 и memory (вычисление внимания на каждом ребре).

Выбор между **GraphSAGE vs GCN vs GAT** производится по тестам **PR-AUC, recall@K, latency p99, silhouette, ECE, memory** (с мониторингом Brier). Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory. Ожидаемый результат: GraphSAGE доминирует по latency p99/memory и индуктивности при сопоставимом PR-AUC/recall@K с GAT; GAT превосходит по PR-AUC на $<1\%$ ценой роста latency p99 в $2$–$3$ раза, что делает GraphSAGE предпочтительным для продукции Spillety.

### 3.6.5. Пространство выбора 4: метод хранения векторов

Точная постановка: выбор метода хранения и поиска векторов осуществляется между вариантами **PQ vs float32** (см. раздел 3.5.4). Сравнение **PQ vs float32** оценивается по тестам **PR-AUC, recall@K, latency p99, silhouette, ECE, memory** (Brier дополнительно). Теоретически мы оцениваем наше решение вот так: PR-AUC, recall@K, latency p99, silhouette, ECE, Brier, memory. Критерий выбора: PQ выбирается тогда и только тогда, когда деградация PR-AUC $<1\%$, recall@K $>0.93$, а экономия memory $\ge 10\times$ компенсирует прирост latency p99 от деквантования ($<0.5$ мс на запрос).

Все четыре пространства выбора — $d \in \{64,128,256\}$, $(M, ef_{construction}, ef_{search}) \in \{16,24,32\} \times \{64,128,256\} \times \{50,100,200\}$, архитектура $\in \{\text{GraphSAGE}, \text{GCN}, \text{GAT}\}$, хранение $\in \{\text{PQ}, \text{float32}\}$ — оцениваются в едином экспериментальном протоколе с фиксацией всех семи метрик.
